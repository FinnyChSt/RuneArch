What it is

Ideas from tools you already know, in one model

RuneArch is for the moment before you write code: when you want to see how a feature crosses the frontend, the backend and the database, agree on it, and hand it off in formats people and tools already understand.

Like dbdiagram

Tables

Typed columns, keys, indexes and foreign keys for PostgreSQL, MySQL, MariaDB or SQLite.

Like Swagger / Apidog

Endpoints

Params, request bodies, responses and reusable models, kept a valid OpenAPI 3.1 spec at all times.

Like wireframing tools

Screens

Low-fidelity layouts on a 12-column grid, whose buttons and forms connect to the endpoints they call.

Like Mermaid flowcharts

Flows

Named paths through the system, recorded click by click and played back step by step.

Like Excalidraw

Sketching

Frames, sticky notes, shapes, arrows and a pen for explaining around the design.

Unlike a drawing

It's a spec

Every box is structured data, so exports are generated live from the canvas and never drift from it.

How it works

From sketch to hand-off in five steps

No code required to plan. Generated code and migrations are there for a developer to review and build from.

Create a project

Start blank, or import tables from SQL or DBML and endpoints from OpenAPI.

Add the parts

Place screens, endpoints, services and tables. Double-click any of them to fill in the details.

Connect them

RuneArch picks what a connection means: a screen calls, a service writes, a column is a foreign key.

Record flows

Click connections in order to tell the story of a user action, then step through it with ← and →.

Export

Preview, copy, download or link to any format from the top bar.

Undo for everything

Every edit is one undo step, and the project autosaves a moment after each change.

Named checkpoints

Save "before the auth refactor" and go back to it. Restoring checkpoints the current state first.

Validated as you type

Duplicate routes, broken foreign keys or unknown models are flagged in the dialog before you save.

Feature scopes

Design changes on top of an existing system

Most work isn't greenfield. You add a wishlist to a shop that already has users, products and orders. A feature tracks exactly what it touches, while you keep designing on the same canvas.

EXISTING

Already built; the feature only uses it, like the users table it reads.

NEW

Added by the feature, like a wishlist_items table. Anything you add is tagged automatically.

CHANGED

Existing but modified. RuneArch keeps the original, shows a diff and lets you revert any change.

REMOVED

Retired by the feature, like an old GET /favorites endpoint.

It warns you, never blocks you

  • NOT NULL columns without a default that need a backfill
  • Breaking API changes, and the version bump they call for
  • New endpoints nothing calls, new tables nothing reads or writes
  • Flows that pass through parts the feature doesn't list
  • Other open features that conflict with this one, or that it depends on

It hands off the whole job

  • Brief (Markdown or JSON): goal, acceptance criteria, flows and every part with its changes. Ready for a developer or an AI coding assistant.
  • Task list per lane: database, backend, frontend.
  • Migration up and down, in the right order, for your database.
  • Ship it to make it the plain project, or discard it to put everything back.

Get started

Run it on your machine

RuneArch is self-hosted. The quickest way in needs only Docker.

With Docker

Then open localhost:8080

git clone https://github.com/FinnyChSt/RuneArch.git
cd RuneArch
docker compose --profile app up -d --build

For development

Node.js 24, pnpm 11, Docker · then localhost:5173

git clone https://github.com/FinnyChSt/RuneArch.git
cd RuneArch
pnpm install
docker compose up -d                # PostgreSQL
cp apps/api/.env.example apps/api/.env
pnpm --filter api db:migrate
pnpm --filter api db:seed           # local user
pnpm dev
Early, working software. There is no sign-in yet: everyone using an instance acts as the same local user, so run it on your own machine or a private network. Two people editing the same project get a conflict notice rather than a live merge. Real authentication and collaboration are planned.
